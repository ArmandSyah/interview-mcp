# Sandbox payment verification, 6 November 2026

The USD 10 monthly sandbox payment workflow passed through the published private website.
The test used real Supabase and Paddle sandbox services, with Paddle's official test card.
No real charge occurred. Public signup remains disabled.

## Deployed correction

The first payment exposed a false conflict in subscription events.
Paddle sent two different events with identical subscription facts and timestamps.
The old dispatcher treated every equal-time event as a conflict and withheld access.
The same condition also affected cancellation events.

Migration `20261106143840_billing_equivalent_events.sql` corrects this comparison.
Matching events preserve the subscription state. Different facts still require reconciliation and block access.
The migration preserves event history, existing conflict flags, ownership checks, and function privileges.
It does not repair earlier conflicts automatically.

## Real service checks

Two fresh, confirmed temporary accounts signed in without email delivery.
Initial status reported no subscription and no access for both accounts.
A checkout request with a caller-supplied account ID returned HTTP 400.
Two concurrent checkout requests returned HTTP 200 and HTTP 409. A retry reused the successful transaction.

The browser loaded the actual private website and its published assets.
It used the site's temporary access header only for that exact website origin.
Supabase and Paddle requests used their real endpoints. No website or payment responses were mocked.
The direct payment link opened Paddle checkout without another checkout POST.
The test card payment completed, and the website displayed active sandbox access after the verified webhook.

The server granted access only to the paying account.
The second account retained no subscription and could not obtain a customer portal link.
The subscribed account could not create a second subscription through checkout.
The website opened `https://sandbox-customer-portal.paddle.com` and displayed the correct subscription product.
Signup controls remained hidden.

Immediate cancellation changed provider status to canceled and removed application access.
The database recorded all four creation and cancellation events without a conflict flag.
Concurrent replacement requests created one checkout for the same customer. A retry reused that replacement.

## Cleanup and limits

The unpaid replacement transaction was canceled.
Both test subscriptions from this verification session were confirmed canceled in Paddle.
Both account pairs were deleted, with HTTP 404 verified after deletion.
The final database check found zero Auth users, zero owned billing customers, and zero noncanceled subscriptions.
Null-owner billing history remains stored as designed.
The earlier false-conflict history remains unchanged and cannot grant access.

Test output contains no card values, passwords, signed portal links, or server keys.
Temporary account credentials were deleted after cleanup. No screenshots or browser traces were recorded.
Paddle hosted the payment form and portal. The application did not receive card numbers or security codes.

This verifies sandbox behavior, not live merchant approval or a public paid service.
Live billing still needs refund and dispute rules, missed-event recovery, request limits, and launch policies.
Public signup needs a later decision and configured email delivery.
The free desktop features remain available without a subscription.
